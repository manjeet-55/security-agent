## Review checklists

Rules a person or an AI assistant checks by reading the code and configuration (`secagent checklist`, MCP `get_checklist`).

### Public surface and APIs (`surface`)

- `surface-auth-by-default` (high): Every route that returns or changes data requires login, or is deliberately public
- `surface-object-ownership` (high): Every lookup by id checks that the record belongs to the caller
- `surface-function-level-authz` (high): Admin and privileged actions check the role on the server
- `surface-response-fields` (medium): Responses return only the fields the client needs
- `surface-rate-limits` (medium): Requests are limited per client, and list and upload sizes are capped
- `surface-docs-and-debug` (medium, in part automated): API docs, GraphQL introspection, debug and management endpoints are off or protected in production
- `surface-inventory` (medium): Old API versions, test routes and non-production environments are not publicly reachable
- `surface-csrf` (medium, in part automated): State-changing requests authenticated by cookies are protected against cross-site request forgery
- `surface-business-flows` (medium): Flows that cost money or can be abused have abuse limits

### Authentication and sessions (`auth`)

- `auth-password-storage` (high): Passwords are hashed with argon2id, bcrypt or scrypt
- `auth-login-throttling` (high): Login, password reset and one-time-code endpoints limit attempts
- `auth-jwt` (high): JWTs are verified with a fixed algorithm, a strong key and an expiry
- `auth-session-lifecycle` (medium, in part automated): Sessions are renewed at login and destroyed at logout
- `auth-password-reset` (high): Reset tokens are random, single-use and short-lived, and the reset link is not built from the request
- `auth-user-enumeration` (low): Login, sign-up and reset do not reveal whether an account exists
- `auth-mfa-admin` (medium): Admin and privileged accounts require multi-factor authentication
- `auth-default-accounts` (high): No default, seeded or test accounts and no master passwords in production
- `auth-oauth` (medium): OAuth and social login check state, exact redirect URIs and token claims

### Input handling (`input`)

- `input-sql-injection` (critical): SQL is built only with parameters, never by joining strings with input
- `input-nosql-injection` (high): Database queries never take objects straight from the request
- `input-command-injection` (critical): No shell command or code is built from input
- `input-xss` (high, in part automated): User content is never inserted into pages as raw HTML
- `input-validation` (medium): Every endpoint validates its input against a schema
- `input-mass-assignment` (high): Request bodies cannot set fields the user should not control
- `input-ssrf` (high): The server does not fetch arbitrary URLs supplied by users
- `input-path-traversal` (high): File paths built from input stay inside their folder
- `input-file-upload` (high): Uploads are limited, checked, renamed and never executed
- `input-open-redirect` (medium): Redirect targets from input are restricted
- `input-deserialization` (high): Untrusted data never creates live objects or changes prototypes
- `input-webhooks` (medium): Incoming webhooks verify their signature, and data from other APIs is validated

### Secrets, configuration and logging (`secrets`)

- `secrets-config-files` (critical, in part automated): No secrets in configuration files, infrastructure code or Terraform state in the repository
- `secrets-client-bundle` (critical, in part automated): No secrets in code that ships to the browser or a mobile app
- `secrets-management` (medium): Production secrets come from a secret store, differ per environment, and can be rotated
- `secrets-debug-off` (high, in part automated): Debug mode and development tools are off in production
- `secrets-error-handling` (medium): Errors shown to users are generic, with no stack traces or internal details
- `secrets-logging` (medium): Security events are logged, and logs hold no secrets or personal data
- `secrets-tls-verification` (high): Connections from the app verify TLS certificates
- `secrets-security-contact` (low): People know how to report a vulnerability to you

### Cloud, containers and supply chain (`infra`)

- `infra-network-exposure` (high, in part automated): Firewalls and security groups open only what must be public
- `infra-storage-public` (high): Storage buckets are private, and public files are shared on purpose
- `infra-iam-least-privilege` (high): Cloud credentials used by the app and CI have only the permissions they need
- `infra-imdsv2` (medium): EC2 instances require IMDSv2
- `infra-account-security` (high): Cloud and code-hosting accounts use MFA, no root keys, and keep audit logs
- `infra-containers` (high): Containers run as non-root, unprivileged, from pinned maintained images
- `infra-dependencies` (high, in part automated): Dependencies are locked, scanned and kept up to date in every ecosystem
- `infra-ci-cd` (high): CI/CD pipelines cannot be turned against you
- `infra-repo-protection` (medium): The main branch is protected and secret scanning blocks pushes
- `infra-patching` (medium, in part automated): Servers, managed runtimes and images get security updates on a schedule
- `infra-backups` (medium): Backups are automatic, encrypted, kept apart, and a restore has been tested
